# Upazila map drilldown — source control and limitations

Current source: user-uploaded `bd_district_map(1).html`; SHA-256 `03c58c72155b5911199be955186ae7c54316da7ea72d6ed057738e0dc2eb2805`. Its separate `UPAZILA_GEOJSON` contains **498 features spanning all 64 district P-codes**. The public map does not use its amCharts dependencies, sample `Math.random()` values, or UI styles. It reuses the existing Leaflet and current design system.

The existing deployed district dataset remains the canonical parent geography with 64 unique `ADM2_PCODE` values. Parent joins use explicit `BD` + first four characters of the uploaded six-digit upazila code. This was verified against every uploaded feature; no normalized-name geography joins are used.

Performance: exported eight static, compressed-friendly assets partitioned by the existing division, loaded only after selecting a district; no upazila geometry increases the initial app/map bundle.

**Critical taxonomy discrepancy:** The production `public.bangladesh_upazilas` table contains **601 rows**, whereas the uploaded file provides **498 polygons**. Exactly **351** source upazila names/aliases uniquely match an existing canonical SQL record within the correct district; those assets carry the verified canonical ID and existing Bengali name. The other **147** geometries have no independently confirmed SQL identity and remain geographic reference only. The dataset also has no independently verified upazila-specific publication date or reuse license. It must not replace, delete, or redefine the current 601-row SQL taxonomy.

**Geometry concern:** Shapely detected a self-intersection in the source's Mehendiganj MultiPolygon (source P-code 100662). It needs a separate source-verified geometry correction before any precise coordinate report attribution to that polygon is treated as authoritative.

**Product scope (reconciled registry navigation):** The existing Explore map now exposes an 8-division selector, 64 district selector and a district-filtered dropdown containing **all 601 canonical project upazila/thana records** from `src/data/upazilas.ts`. These choices use the same IDs/names as the unchanged production `bangladesh_upazilas` table; division/district selections share the existing public Explore filter state. Exactly 351 entries have uniquely matched historical polygon identities. The other **250 registry entries remain selectable and display 'boundary not verified'** instead of guessed outlines or counts. In addition to the 601 canonical choices, the 147 unmatched historical polygons are explicitly separated and labelled *unverified historic shapes* (never counted as valid current registry entries). Full details and the per-entry 601/498 crosswalk are in `docs/upazila-map-coverage-crosswalk.json`. Clicking supported polygons, selecting by dropdown, back navigation and keyboard navigation reuse the existing system. Selecting a location without a polygon restores the district overview rather than leaving the map centered on a different upazila.

**Previous map contract:** Selecting a district exposes the available upazila polygons, a dropdown, click/keyboard selection, a back action, and coordinate-confirmed public reports when available. Text-only district reports are never guessed into upazilas. Existing report filters, forms, publication, SQL, admin, mobile, EN/BN, theme modes, and density/point layers remain unchanged. For historical polygons without an independently verified Bengali label, retain the source English name rather than fabricate a translation.

**Current privacy limitation:** The existing sanitized public report RPC intentionally does not expose precise coordinates, and the public report mapper explicitly leaves coordinates undefined. The upazila polygons can be explored and selected, but accurate report counts or a real upazila-level report filter are not available in the current public data contract. Do not treat zero coordinate-confirmed matches as zero incidents. A future authorized privacy-preserving aggregate could enable upazila report statistics, but only after source reconciliation and explicit data-contract review.\n\n**Not completed by the uploaded file:** Authoritative and current coverage for all 601 canonical upazilas, SQL-level location consistency for the 147 unmatched shapes, upazila attribution for location-text-only published reports, or full public/SQL/admin upazila filtering. Reconcile those separately with source-verified official geographic and report-location evidence before claiming complete upazila-level reporting.

**Definition warning:** The project's 601-count registry deliberately combines rural **upazilas** with metropolitan police **thanas**. It is not a verified claim that the country has 601 government upazilas. The public Bangladesh National Portal's dated 2022 office inventory separately listed 495 upazilas (https://bangladesh.gov.bd/site/page/51ae2125-d2f7-430e-8558-53bf94990d0d/govt.-office-info), while Bangladesh Police documents separate metropolitan police-station jurisdictions (https://www.police.gov.bd/en/dhaka_metropolitan_police). Those historical/sector-specific counts cannot substitute for an authenticated 2026 combined-area GIS crosswalk. The external geoBoundaries ADM3 listing contains 544 geometries sourced to 2020/2023 metadata and therefore likewise does not establish all 601 jurisdiction polygons (https://www.geoboundaries.org/api/current/gbOpen/BGD/ADM3/). To make polygon coverage genuinely 100%, obtain official or explicitly licensed district-specific upazila boundaries **and separate metropolitan thana jurisdiction polygons**, uniquely reconcile IDs against all 601 records, verify geometry topology and temporal applicability, and then revise both public/admin without disclosing suppressed report coordinates. Current release does not fabricate missing geometry.
